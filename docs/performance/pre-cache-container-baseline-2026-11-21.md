## Method

- Seven read scenarios
- 300 measured requests per scenario, 2,100 total requests per run
- Concurrency: 20
- Ten sequential warm-up requests before each measured scenario
- All measured responses required HTTP 200
- RocketMQ and XXL-JOB disabled
- Application health required `UP` before the run

The first complete run was treated as a cold-environment run. The second complete run immediately
followed it and is the warm comparison baseline below.

## Observations

1. The broad title-prefix query is the dominant cache candidate. MySQL 8.4.7 selected the primary-key
   range scan, examined 90,126 book rows, and reported about 55.1 ms for one isolated execution.
   At concurrency 20, the complete HTTP path reached p50 1.50 seconds and p95 2.25 seconds.
2. The application and MySQL cgroups both recorded CPU throttling during setup and the two runs.
   Application throttled periods: 75. MySQL throttled periods: 500. Neither container recorded an OOM,
   OOM kill, or memory-limit event.
3. Application and MySQL logs contained no `ERROR`, `Exception`, `FATAL`, or panic lines after the run.
4. Catalog responses include dynamic availability. Post-cache verification must cover borrow, return,
   stock resize, publish, and offline transitions so latency gains do not hide stale availability.
